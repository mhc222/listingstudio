# Listing Studio — full UI/UX review

Date: 2026-09-03 · Reviewer: read-only pass · Scope: golden path from fresh upload to delivered edit

## Method and its limits

The dev server on port 3000 was up and answering (`/` 200 in 65 ms, `/login` 200 in 244 ms, `/dashboard` 307 → `/login` in 5 ms). **The Chrome extension was not connected** (`tabs_context_mcp` returned "Browser extension is not connected", `list_connected_browsers` returned `[]`), so no live click-through and no screenshots were possible. An attempt to mint a read-only session cookie via the project's own `scripts/mint-session.mjs` recipe was blocked by the sandbox classifier, so authenticated pages could not be fetched over HTTP either.

This review is therefore a **static walk of the route tree and components**, plus HTTP timing on the public routes. Every claim below cites the file and line responsible. Numbers marked *(computed)* are derived from the markup — layout arithmetic, awaits counted in source, round-trips counted in source — not measured in a browser. Numbers marked *(measured)* came from curl. Nothing here is a guess dressed as an observation, but the layout heights and wait durations should be confirmed with a real browser pass before anyone spends a week on them.

No paid generation was submitted, no source file was modified, no build was run.

## 1. Executive summary

1. Matt is right, and the cause is not the number of clicks — a fresh upload to one finished edit is about **10 clicks**, which is competitive. It is **latency, image weight, and visual churn**.
2. **No thumbnails exist anywhere in the product.** Every photo surface renders the full-resolution original: the tray, the batch grid, the proofing contact sheet, even 100-px reference pickers. `next/image` is deliberately disabled on all of them.
3. A 24-photo shoot of 8 MB originals therefore downloads **~190 MB just to draw the photo tray**, and the same again for proofing.
4. Worse, `router.refresh()` is called constantly, and each refresh re-mints every signed URL. New URL string = new download. The full image set re-downloads **every 5 seconds while an edit runs** and roughly **every 350 ms during an upload**.
5. Three realtime subscriptions listen to `upload_items`, `file_groups`, and `output_versions` **with no listing filter and no debounce**, so unrelated writes trigger full server re-renders of a 13-query page.
6. The photos — supposedly "the object of work" — start roughly **1,700 px down the listing page**, behind four stacked organization panels, two separate six-tile counter grids, and three different room-filter controls.
7. `POST /api/jobs` runs **two sequential per-photo loops**, the second one making an external fal call per photo. The studio modal is frozen on "Starting edit…" for all of it.
8. The task rail holds 6 tasks + More in a 320-px column with the scrollbar hidden — **"Renovate" and "Change color" are simply not visible** when the studio opens.
9. Proofing has no bulk or keyboard approve: 24 finals = **48 clicks**, each one re-downloading the whole contact sheet.
10. The mobile sticky action footer required by UI-SPEC.md is `md:sticky` — **desktop only**. There is no safe-area padding anywhere in the codebase.

## 3. Top 10 friction points, ranked by impact

### 1. Every photo surface downloads the full-resolution original

No derivative pipeline exists. No `thumb` column in any migration, no Supabase image transform in `lib/storage.ts`, and `next/image` is disabled by an eslint-disable on every listing photo (10 call sites). The tray (`photo-grid.tsx:184`) paints a ~300 px card from an 8 MB file. The composer's "Apply these settings to another view" picker renders **every other photo in the listing** at ~100 px wide, full-res (`composer.tsx:908`). Proofing does it at 136 px.

*Impact:* ~190 MB to draw a 24-photo tray *(computed)*. This alone accounts for "it takes a while."
*Files:* `lib/storage.ts:45`, `photo-grid.tsx:184`, `proofing-workspace.tsx:654`, `composer.tsx:908`, `listing-workspace.tsx:404,468`.

### 2. `router.refresh()` re-mints signed URLs, so refresh = re-download everything

`getUrls` calls `createSignedUrls` with a 3600 s expiry. The expiry is baked into the token, so any two calls more than a second apart return **different URL strings**. React sees a new `src`, the browser refetches. Combined with the refresh triggers below, the entire image set is re-downloaded on a timer.

*Impact:* turns finding #1 from a one-time cost into a continuous one. Directly produces flicker.
*Files:* `lib/storage.ts:45-57`; refresh callers `listing-progress.tsx:60-77`, `file-group-workspace.tsx:271-283`, `upload-queue.tsx:183`, `proofing-workspace.tsx:261`.

### 3. Unfiltered, undebounced realtime subscriptions on a 13-query page

`ListingProgress` subscribes to 8 tables. Three have **no filter**: `upload_items`, `file_groups`, `output_versions`. Every matching write anywhere in the database calls `router.refresh()` with no debounce. The result workspace repeats the mistake for `file_groups` and `output_versions`.

*Impact:* an unrelated background webhook re-renders the listing page and re-downloads the tray.
*Files:* `listing-progress.tsx:44-56` (lines 46, 51, 52), `file-group-workspace.tsx:230-231`.

### 4. ~1,700 px of panels above the photos

The listing page stacks: hero → ToolsNav → **Current workflow** (6 counter tiles, always rendered even when every count is zero) → **Upload queue** + "After upload" preset → **Shoot inventory** (a *second* 6-tile counter grid) → **Room review** (4 filter chips) → **Rooms & photos** (a room picker) → **Batch selection** (a third row of room chips) → "Photos (N)" → the photos. None of the four organization panels collapse when idle; all three return a full `ls-surface` unconditionally.

Two six-tile counter grids and three separate room controls, one above the other, is the panel churn. UI-SPEC.md principle 1 says the photo stays visually dominant from selection through delivery; here it is below the fold on every visit.

*Impact:* the app feels like a form to be processed, not a studio.
*Files:* `app/listings/[id]/page.tsx:157-215`, `listing-progress.tsx:79-124`, `shoot-organization.tsx:107-127`, `room-organization.tsx:132-172`, `room-browser.tsx:290-300`, `listing-workspace.tsx:290-350`.

### 5. `POST /api/jobs` serializes everything, and the modal is frozen for all of it

Two sequential `for` loops. The first inserts one `file_group` per photo, one round-trip each. The second calls `submitStep` per photo, each doing ~7 sequential awaits including an **external fal POST with a retry-and-backoff path**. Plus ~10 preflight round-trips and a sequential `use_count` update loop. Only then does the client `router.push`, which triggers a *full server render* of the result page — with no skeleton and no optimistic navigation.

*Impact:* the dead time after "Start edit" scales linearly with batch size while the UI shows one static disabled button.
*Files:* `app/api/jobs/route.ts:358-447` (loops at 358 and 445), `lib/orchestrator.ts:179-232`, `composer.tsx:395-397`.

### 6. Proofing costs two clicks per photo with no bulk or keyboard path

Arrow keys move the selection; approving is mouse-only. No "Approve all", no `A` shortcut, no "approve everything that passed QA". Each approval POSTs and then `router.refresh()`es the whole page.

*Impact:* 48 clicks and 24 full-page refreshes to close out one shoot. Frame.io and Autoenhance both make this a keyboard pass.
*File:* `proofing-workspace.tsx:414-425` (keyboard handler), `:261` (refresh), `:783-791` (approve buttons).

### 7. Two of six primary tasks are invisible when the studio opens

The rail is `overflow-x-auto` with the scrollbar explicitly hidden. Six icon+label buttons plus More come to roughly 660 px *(computed)* inside a rail the grid caps at `minmax(20rem, 23.5rem)`. Renovate and Change color fall off the right edge with no visual cue. UI-SPEC.md line 209 asks for "a compact two-column list, not marketing cards" — which would fit.

*Impact:* the product looks like it has four tasks.
*File:* `composer.tsx:93-100` (rail), `listing-workspace.tsx:399` (rail width).

### 8. The mobile studio has no sticky footer and no safe-area padding

The action footer is `md:sticky md:bottom-0` — sticky on desktop, inline on phones. So on mobile you scroll past the task rail, presets, the describe box, the chain editor, the views picker, the add-edit disclosure, the reference strip and the notes field to reach "Start edit". `grep -rn "safe-area\|env(safe"` across `app/`, `components/` and `lib/` returns **nothing**, so the last control sits under the home indicator. Both are explicit UI-SPEC.md requirements ("sticky action footer"; "safe-area padding is included"). The canvas is also `max-h-[48vh]` against a 42vh cap in spec.

*Impact:* the phone golden path is materially worse than the spec Phase 54 claims to have hardened.
*Files:* `composer.tsx:934` (footer), `listing-workspace.tsx:404` (48vh).

### 9. The studio modal is hand-rolled and unpolished

`fixed inset-0` conditional render: no enter/exit transition, no body scroll lock (the page scrolls behind the overlay), a hand-written focus trap duplicated for the single and batch variants, and `Escape` handling wired through a `window` listener. The app has a real motion system in `globals.css` (`--ease-fluid`, `ls-mode-panel-in`, a `prefers-reduced-motion` block) — the modal simply does not use it.

*Impact:* the one moment that should feel like a lens opening feels like a hard cut. This is a large part of "not slick."
*File:* `listing-workspace.tsx:118-157` (trap), `:385-395` and `:447-455` (both overlays).

### 10. Delivery blocks the first package behind an 8-field form

No profile is seeded. Until one is named and saved, the preview pane says only "Save a profile to preview this package."

*Impact:* the last step of the golden path opens with homework instead of a preview.
*File:* `delivery-workspace.tsx:227-250`, `:265`.

**Also worth noting, below the top 10:** the listing server component fetches *all* jobs with *all* file groups, output versions and chat messages, unbounded, then signs a URL for every output version ever created (`page.tsx:44-52, 106`) — so the page gets slower for the rest of the listing's life. Composer's entry state also renders the preset panel, the reference-image strip, the output-size select and the estimate line *before* a task is chosen, which is four sections more than UI-SPEC.md's entry state. And `ToolsNav` puts Aerial/Reel/Tour/Plan/Copy in positions 2–6, pushing Proofing and Delivery — the actual golden path — to the end, where they scroll off-screen on a phone.

## 4. Proposed target flow

What the slick version looks like. Same information architecture, same safety guarantees, same routes — the changes are weight, motion and where work happens.

**Step 1 — Open the listing.** Hero collapses to a 96-px bar with address, cover crop and one status line ("18 ready · 2 editing · 4 need review"). The photo tray is **the first thing below it**, at roughly 400 px down instead of 1,700. Every organization panel becomes a chip in a single toolbar above the tray — `Shoot inventory · 24` / `Rooms · 6 untagged` / `HDR · 2 stacks` — each expanding *in place* on click. Zero-state panels do not render. One room control, not three.

**Step 2 — Upload.** Drag onto the tray itself. Each file appears **immediately as an optimistic tile** with a determinate ring, using the local `File` as a `blob:` preview so nothing is downloaded to draw it. Rows keep the existing Waiting/Uploading/Finalizing/Uploaded/Needs attention truth. No page refresh during the upload — the queue patches its own tiles, and a single `router.refresh()` fires once when the batch finishes.

**Step 3 — Organize.** Unchanged in substance; it is already the strongest part of the build. It just lives in the toolbar chips, deliberate as it is today, instead of owning three full-width panels above the work.

**Step 4 — Open a photo.** Click the tile. The tile's thumbnail **scales into the studio canvas** (~200 ms, `--ease-fluid`, skipped under reduced motion) while the full-resolution original loads behind it. Body scroll locks. The rail slides in.

**Step 5 — Compose.** Tasks are a **two-column grid of six**, all visible, per spec. The rail shows only the chosen task's controls; presets, references, output size and the estimate move under Advanced until a task is picked. The footer is sticky at *all* widths, with `env(safe-area-inset-bottom)`.

**Step 6 — Start edit.** The click **navigates immediately** to the result workspace, which renders a skeleton over the source photo. `POST /api/jobs` returns as soon as the job and file groups are written (one batched insert, not a loop); `submitStep` fan-out moves to `Promise.all` behind the existing concurrency gate, or to a queue drain the reconcile cron already knows how to finish. The modal never freezes because it is already gone.

**Step 7 — Watch it develop.** Realtime only, filtered by listing. Where polling is still needed locally, it patches state through a fetch instead of `router.refresh()`, and **signed URLs are stable** — minted once per path per page load and cached — so the source photo never flickers.

**Step 8 — Review.** Result dominant, before/after, Download, Refine. Already right; leave it alone.

**Step 9 — Proof.** Contact sheet on **thumbnails**. `←`/`→` moves, `A` approves, `N` marks needs-changes, `Space` toggles before/after. "Approve all passing QA" as one action with an explicit count. Approvals patch the row optimistically; no page refresh per photo.

**Step 10 — Deliver.** One "MLS 1920 JPEG" profile seeded on first visit, so the preview is populated the moment the page opens. The 8-field form stays, behind Edit.

## 5. Quick wins vs larger redesigns

### Quick wins — days, no schema change, no new concepts

| Fix | Where | Why it pays |
|---|---|---|
| Cache signed URLs per path per render instead of re-minting | `lib/storage.ts:45` | Kills the flicker and the re-download storm in one place. Highest value-to-effort ratio in this list. |
| Add listing filters to the three unfiltered realtime subscriptions, and debounce refresh to ~1 s | `listing-progress.tsx:46,51,52`; `file-group-workspace.tsx:230-231` | Stops unrelated writes re-rendering a 13-query page. |
| Stop `router.refresh()` per upload item; patch the queue locally, refresh once at batch end | `upload-queue.tsx:183` | Removes the worst-feeling moment in the product. |
| Return `null` from the four organization panels when they have nothing to say | `listing-progress.tsx`, `shoot-organization.tsx`, `room-organization.tsx`, `room-browser.tsx` | Recovers ~600 px above the photos for the cost of four guard clauses. |
| Make the footer sticky at all widths and add `env(safe-area-inset-bottom)` | `composer.tsx:934` | Closes a stated UI-SPEC violation. |
| Task rail → two-column grid of six | `composer.tsx:93` | Makes two hidden tasks visible. Spec already asks for this. |
| Modal: add `overflow:hidden` on body and a 200 ms enter transition | `listing-workspace.tsx:385,447` | The cheapest available "slick". The motion system already exists. |
| Add `A` / `N` keyboard approve in proofing | `proofing-workspace.tsx:414` | Turns 48 clicks into a keyboard pass. |
| Seed one default delivery profile | `delivery-workspace.tsx` | First delivery shows a preview instead of a form. |
| Batch the `file_group` inserts; `Promise.all` the `submitStep` fan-out | `app/api/jobs/route.ts:358,445` | Cuts batch submit from linear to roughly constant. |

### Larger redesigns — worth planning, not worth starting blind

1. **A thumbnail pipeline.** The real fix for findings #1 and #2. Generate a ~400 px WebP derivative on upload finalize (sharp is already a dependency), store it beside the original, and serve it to every grid, tray, contact sheet and picker. Originals stay immutable, which is the whole point. This is the single largest perceived-speed win available and everything else is a rounding error next to it.
2. **Listing page recomposition.** Photos first, organization as expanding toolbar chips, one room control instead of three. Real information-architecture work, and it needs a browser pass to tune — but it is what turns the page from a processing form into a studio.
3. **Optimistic submit and navigation.** Navigate on click, skeleton on the result page, job creation and fal fan-out decoupled behind the existing gate and reconcile cron. Touches orchestration, so it needs care — the idempotency and single-ledger-write guarantees in CLAUDE.md must survive intact.
4. **Bounded listing queries.** Paginate or scope the unbounded jobs/output-versions fetch so the listing page does not degrade with history.
5. **Proofing as a review queue.** Keyboard-first traversal, optimistic approvals, "approve all passing QA".

### Do not reopen

42-UX-BENCHMARK.md's freeze decision holds and this review found nothing to overturn it. Typography, radii, the brass/linen palette, spacing density, staging-preview curation: leave frozen. **None of what makes this feel clunky is visual taste.** It is image weight, refresh discipline, sequential server work, and 1,700 px of panels standing between Matt and his photos.
